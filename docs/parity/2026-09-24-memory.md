# HTDemucs memory and throughput on CPU, 2026-09-24

Replication cell P1 from the audit plan: peak RSS and real-time factor of
one full separation, one ONNX Runtime option at a time.

## Stamp

- charon: commit `c202058` plus the `OnnxOptions` change committed as
  `1e9451c`; `cargo build --release --example profile`, default features.
  ort `=2.0.0-rc.13`, ONNX Runtime 1.28.0, CPU execution provider.
- Model: `htdemucs.onnx` (SHA-256 `68d0bf16...5fcc5e74`, 316 MB) and
  `htdemucs_fp16weights.onnx` (SHA-256 `d05c269d...745db70a`, 166 MB).
- Input: 192.6 s stereo 44.1 kHz float WAV (the `audioknap-blockbuster`
  track from the real-tracks record), decoded once before timing.
- Host: Apple M4 Pro (14 cores), 24 GB, macOS 26.6. Nothing else running.
- Method: `examples/profile.rs`. `rss_load` is `ru_maxrss` after
  `Separator::new`, `peak` after separation. `separate_s` is wall time of
  `Separator::separate` (no decode, no write). Each cell is a fresh
  process; the two runs inside a process agree within 2%, the first run
  is reported. `checksum` is the sum of all output samples; it changes
  only when the graph optimization level changes.

A shell quoting error invalidated the first multi-key cells (zsh passed
`"a=1 b=0"` as one argument, so only the first key applied, with a garbage
value). Every row below was either a single-key cell or re-run with
proper splitting.

## Reading

1. **The memory is at load, and it is constant folding.** With ORT
   defaults the session takes 4.6 GB before the first run, for a 316 MB
   file. Disabling the `ConstantFolding` transformer (or all
   optimization) brings load to 0.7 GB. The export computes its STFT
   index tensors with Range/Expand/ScatterND subgraphs (684 ScatterND
   nodes); folding materializes them as constants, about 3.8 GB.
2. **Memory pattern costs 1 GB of peak at run time and buys nothing
   here.** Same throughput with it off in every pairing.
3. **The arena does not matter for peak** once folding is off.
4. **fp16 weights do not help.** Same peak within 1%; the weights are
   not where the memory goes.
5. **Cost of the low-memory setting: 11% throughput** (RTF 8.47 vs 9.44)
   and 1.8 s more load time (the folded constants are recomputed per
   run).
6. Threads: all 14 cores give RTF 9.4; 8 cores 9.0; 4 cores 7.4.

Decision for 0.1.1: `OnnxOptions::low_memory()` (ConstantFolding off,
memory pattern off) is the HTDemucs preset default. Peak goes from
5.58 GB to 2.12 GB (-62%). `OnnxOptions::max_speed()` restores ORT
defaults. The remaining 1.4 GB of run-time growth is activations for one
7.8 s segment and is the next target.

The model card's "~1.1 GB" claim was not reproduced under any setting on
this host; the lowest observed peak is 2.1 GB, and the lowest observed
post-load RSS is 0.7 GB.

## CoreML execution provider: does not run this model

Tried with the `ort` `coreml` feature (ONNX Runtime 1.28.0 CoreML EP),
CPU EP as fallback, same input, in four configurations. All failed:

| configuration | failure |
|---|---|
| MLProgram, static input shapes, ComputeUnits::All (no cache dir) | `SaveModel Saving the CoreML model failed` (temp path) |
| MLProgram, static input shapes, All, on-disk cache dir | compiles; run fails: `Slice ... Ends must be a 1-D array` |
| MLProgram, dynamic shapes, All | `Failed to create MLModel, error: Error in building plan` |
| NeuralNetwork format, static shapes, All | run fails: `/crosstransformer/layers.0/self_attn/Reshape` shape error |
| MLProgram, static shapes, CPUAndGPU | `Slice ... Ends must be a 1-D array` |

The graph partitioning between CoreML and CPU breaks rank/shape
contracts on Slice and Reshape. This is an ORT CoreML EP limitation on
this export, not something charon controls. The `coreml` feature was
removed from 0.1.1 rather than shipped as a non-working switch. It
returns when a configuration is measured to run.
